2. RESUMEN DEL PROYECTO
-------------------------------------------------------------------------------

Cliente  : Duena de un local que organiza eventos tematicos (pintura,
           escritura, charlas, etc.). Cada evento dura tipicamente 2 horas.
Necesidad: Automatizar el flujo de reserva que hoy se hace 1 a 1 por WhatsApp.
Alcance  : Aplicacion web mobile-first para que los clientes vean eventos
           proximos, reserven su lugar y paguen por transferencia; y un panel
           privado donde la duena administra eventos y valida pagos.
Stack    : Next.js 16.4 + TypeScript + Tailwind v4 + Postgres + Drizzle + Supabase
Base dev : Postgres 18 LOCAL (ya estaba instalado en la maquina). Supabase queda
           para el despliegue. Es el mismo motor, asi que el esquema no cambia
           y no hay que reescribir nada al migrar.

3. DECISIONES TOMADAS (ETAPA 1 - DISCOVERY)
-------------------------------------------------------------------------------

3.1 PAGO
    - Se cobra por TRANSFERENCIA al alias de MercadoLibre del local.
    - El cliente sube el comprobante (foto o PDF).
    - La verificacion del pago es 100% MANUAL por la duena.
    - Se descarto la integracion automatica con MercadoPago (comision).
    - Se dejo asentado que el comprobante es falsificable: la unica validacion
      real es la revision humana. Para acelerarla se le piden al cliente los
      datos declarados de la transferencia (titular, monto, fecha, nro. de
      operacion). Es una funcion de EFICIENCIA, no de seguridad.

3.2 CUPOS Y ESTADOS
    - 1 reserva = 1 persona = 1 lugar. Sin acompanantes en el mismo formulario.
    - Una reserva por persona por evento (dedupe por mail / WhatsApp).
    - El cupo se retiene AL ENVIAR EL FORMULARIO, no al subir el comprobante.
      Motivo: si el cupo se toma al final, el ultimo lugar puede perderse
      despues de que la persona ya transfirio el dinero.
    - Existen DOS pendientes distintos:
        * Pendiente SIN comprobante: ocupa cupo y se libera por timer (30 min).
        * Pendiente CON comprobante: ocupa cupo y NO expira por timer. Solo se
          libera por decision de la duena (aprobar o rechazar).
    - La reserva mantiene el lugar retenido hasta que la duena resuelva.

3.3 PRECIO
    - Todos los eventos tienen precio obligatorio y se paga el TOTAL
      (no se cobra sena).

3.4 FORMULARIO DE RESERVA
    - Datos personales: nombre y apellido, email y WhatsApp (los tres
      obligatorios).
    - Condiciones o limitantes (OBLIGATORIO responder si / no): celiaquia,
      diabetes, movilidad reducida, etc. Si la respuesta es "si", se abre un
      campo de texto para describir cual, y ese texto pasa a ser obligatorio.
    - Datos declarados de la transferencia: titular, monto, fecha, nro. de
      operacion.
    - Adjunto: comprobante (foto o PDF, con limite de tamano).
    - Checkbox de terminos y condiciones: OBLIGATORIO.
    - Checkbox "acepto recibir novedades por mail": OPCIONAL y SEPARADO del
      anterior. Debe ser separado porque un consentimiento de marketing
      embebido en los terminos no es valido legalmente.

3.5 NOTIFICACIONES
    - NO se envian emails automaticos al cliente en v1.
    - WhatsApp automatico: se evaluaron tres caminos.
        * Cloud API oficial de Meta: automatizable, pero exige verificacion de
          negocio, un numero aparte y plantillas pre-aprobadas. Tiene costo.
        * Deep link desde el panel (RECOMENDADO): un boton abre WhatsApp con
          el mensaje ya escrito y la duena solo aprieta enviar. Gratis.
        * Librerias no oficiales (Baileys): DESCARTADO. Riesgo de banear el
          numero del negocio, que es el mismo que sostiene la operacion.
    - El cliente consulta el estado de su reserva en una pagina publica con
      link secreto (token). Es el unico canal de seguimiento en v1.
    - El envio de notificaciones queda encapsulado en un solo modulo, para que
      migrar de deep link a Cloud API mas adelante no toque otras funciones.

3.6 ADMINISTRACION
    - Un solo usuario administrador (la duena) con usuario y contrasena y
      cookie de sesion. Sin OAuth, sin roles, sin multi-tenant.

3.7 LEGAL
    - Las condiciones de salud son DATOS SENSIBLES segun la Ley 25.326 de
      Proteccion de Datos Personales. Requieren consentimiento explicito y no
      pueden usarse para marketing ni compartirse con terceros.

3.8 GIT
    - El repositorio lo maneja el usuario. El agente NO hace commit ni push.

3.9 BASE DE DATOS EN DESARROLLO (agregado en Etapa 2)
    - Se descarto crear el proyecto en Supabase en este momento: el pedido fue
      poder probar el sistema localmente sin depender de una cuenta externa.
    - La maquina ya tenia PostgreSQL 18 instalado como servicio
      (postgresql-x64-18). Se decidio usarlo en lugar de instalar algo nuevo.
    - Por que NO se uso una base embebida tipo PGlite o SQLite: la restriccion
      R1 (reservar el cupo con transaccion y lock) es justamente lo que hay que
      probar, y para probar concurrencia real hace falta un motor real con
      conexiones concurrentes. Una base embebida de una sola conexion daria una
      falsa sensacion de seguridad en el punto mas delicado del sistema.
    - Postgres local y Supabase son el MISMO motor: el esquema, la migracion y
      las consultas sirven igual en los dos. Cambiar de uno a otro es cambiar
      una variable de entorno, no reescribir codigo.
    - La aplicacion se conecta con un rol propio (casa_de_anton), nunca con el
      superusuario postgres.

4. RESTRICCIONES TECNICAS NO NEGOCIABLES
-------------------------------------------------------------------------------

    R1. El cupo se reserva con TRANSACCION y lock en la base de datos. Nunca
        un "if (hay lugar)" en el codigo de aplicacion. Es el bug clasico de
        los sistemas de reservas: dos personas reservan el ultimo lugar al
        mismo tiempo y se vende de mas.
    R2. Los comprobantes viven en almacenamiento PRIVADO y se sirven con URL
        firmada que expira. Contienen datos personales y datos sensibles.
    R3. El vencimiento de reservas sin comprobante se calcula en la consulta.
        Sin cron, sin colas de trabajo, sin Redis.
    R4. El formulario debe funcionar en celular con red inestable: compresion
        de imagen en el cliente y reintento visible.
    R5. Mobile-first real: el formulario corto y la accion principal alcanzable
        con el pulgar.

6. HALLAZGOS DE NEXT 16 (MAPEO DE DOCUMENTACION)
-------------------------------------------------------------------------------

El proyecto genero un archivo AGENTS.md que advierte que Next 16 tiene CAMBIOS
ROMPIENTES respecto de versiones anteriores y exige leer la documentacion
incluida en node_modules/next/dist/docs/ antes de escribir codigo. Se mapeo esa
documentacion. Hallazgos que afectan directamente a este proyecto:

    H1. cacheComponents ya viene ACTIVADO por defecto en este scaffold
        (next.config.ts). Consecuencia: los datos se buscan de forma dinamica
        por defecto y el cacheo es OPT-IN, declarandolo con la directiva
        'use cache'. Es el cambio mas grande respecto de lo conocido y la
        fuente mas probable de un bug sutil.

    H2. cookies(), headers(), params y searchParams son PROMESAS. Hay que
        hacerles await. El acceso sincrono ya no existe.

    H3. middleware.ts esta DEPRECADO y renombrado a proxy.ts, y corre solo en
        runtime Node (no edge).

    H4. revalidateTag ahora exige un segundo argumento (perfil de cacheLife).
        Se agregan updateTag y refresh, exclusivos de Server Actions.

    H5. LIMITE QUE AFECTA NUESTRO CASO: el cuerpo de una Server Action esta
        limitado a 1 MB por defecto. Una foto de celular pesa entre 3 y 8 MB,
        asi que el comprobante NO se puede subir por una Server Action sin
        ampliar ese limite. Decision pendiente para la tarea T6 (ver P4).

    H6. redirect() lanza una excepcion interna: no debe llamarse dentro de un
        try/catch.

    H7. next lint fue removido y el build ya no corre linting automaticamente.

    H8. Node.js 20.9+ y TypeScript 5.1+ son obligatorios. El entorno cumple.

REGLA OPERATIVA FIJADA: no se escribe codigo de aplicacion basandose en memoria
de versiones anteriores de Next. Se consulta la documentacion local del paquete.

12. RECUPERAR LA CONTRASENA DE POSTGRES (procedimiento, por si vuelve a pasar)
-------------------------------------------------------------------------------

Si algun dia se vuelve a olvidar la contrasena del superusuario postgres, este
es el procedimiento. NO es exclusivo de este proyecto: sirve para cualquier
PostgreSQL en Windows.

  Requisitos: permiso de escritura sobre la carpeta de datos y UNA consola
  elevada. Nada mas.

  PASO 1 - Copia de seguridad de la configuracion de autenticacion

    Copy-Item 'E:\PostgresSQL\data\pg_hba.conf' 'E:\PostgresSQL\data\pg_hba.conf.cda-backup' -Force

  PASO 2 - Habilitar temporalmente el acceso local sin contrasena

    Reemplazar scram-sha-256 por trust SOLO en las lineas que apuntan a
    127.0.0.1 y ::1. NUNCA en las lineas que no son de loopback: eso abriria
    la base a la red entera.

  PASO 3 - Recargar la configuracion (requiere consola de administrador)

    & 'E:\PostgresSQL\bin\pg_ctl.exe' reload -D 'E:\PostgresSQL\data'

    Debe responder: server signaled

  PASO 4 - Cambiar la contrasena (no pide la anterior)

    & "E:\PostgresSQL\bin\psql.exe" -U postgres -h 127.0.0.1 -c "ALTER USER postgres WITH PASSWORD 'la-nueva';"

  PASO 5 - RESTAURAR la configuracion original

    Copy-Item 'E:\PostgresSQL\data\pg_hba.conf.cda-backup' 'E:\PostgresSQL\data\pg_hba.conf' -Force

  PASO 6 - Recargar de nuevo, con la consola elevada (Paso 3 otra vez).

  PASO 7 - VERIFICAR QUE LA SEGURIDAD VOLVIO

    Conectar sin contrasena TIENE que ser rechazado. Si entra, la configuracion
    no se restauro bien.

  ADVERTENCIA IMPORTANTE: entre el Paso 3 y el Paso 6, cualquiera que pueda
  conectarse a la maquina puede entrar como superusuario sin contrasena. La
  ventana debe durar segundos, solo se habilita en loopback, y hay que
  asegurarse de restaurar siempre. Verificar el Paso 7 no es opcional.

  Lo que NO se puede hacer sin permisos de administrador: recargar la
  configuracion. Ese paso lo tiene que hacer una persona.

14. LA REVISION AUTOMATICA (RDD) - QUE ES Y COMO SE COMPORTA
-------------------------------------------------------------------------------

QUE ES: "receipt-driven development" es un sistema de revision que viene con
gentle-ai. Cuando termina una unidad de trabajo evalua el RIESGO del cambio y,
si corresponde, lanza revisores independientes que buscan problemas antes de
dar la tarea por cerrada.

ESTA ENCENDIDO A NIVEL GLOBAL. O sea: no es una decision tomada para este
proyecto, es una configuracion global que aplica a TODO proyecto donde se use
este entorno. Se puede consultar y apagar:

    gentle-ai review mode status                          consulta, no cambia nada
    gentle-ai review mode disable --scope clone --cwd .    apaga solo este proyecto
    gentle-ai review mode enable  --scope global           prende global

ESTADO EN ESTE PROYECTO: encendido, pero T4 NO pudo ser revisado.

  Motivo, sin vueltas: la revision funciona comparando contra un commit
  anterior. Cuando se hizo la linea base, T4 ya estaba terminado y adentro de
  ese commit. Entonces no existe un "antes de T4" contra el cual compararlo, y
  la herramienta lo dice ella misma:

    "the review assess candidate has no pending changes; already-committed work
     can be assessed by rerunning review assess --base-ref <commit>"

  Se decidio NO fabricar una comparacion falsa ni revisar el proyecto entero
  como si fuera un solo cambio: eso seria teatro, no verificacion. T4 ya esta
  verificado con evidencia real (codigo HTTP medido con curl, cupos probados
  contra la base, tsc y build limpios), que para esta tarea vale mas que una
  revision formal.

  LECCION PARA T5 EN ADELANTE: para que la revision sirva, la linea base tiene
  que existir ANTES de empezar la tarea, y la tarea se cierra con su propio
  commit. Recien ahi la revision tiene un cambio real que mirar. Y T5 es,
  justamente, la tarea donde mas vale la pena: ahi nacen la transaccion y el
  bloqueo, o sea la parte del sistema donde un error se paga con plata del
  cliente.

DECISIONES QUE CONVIENE ENTENDER

  1. NO SE BORRA UN EVENTO. Las claves foraneas son ON DELETE RESTRICT: si el
     evento tiene reservas, borrarlo falla en la base. Borrar un evento con
     reservas no es un detalle tecnico, es una decision de negocio (que pasa
     con la plata y con la gente anotada), asi que T8 no la toma.

  2. NO SE PUEDE BAJAR LA CAPACIDAD POR DEBAJO DE LOS LUGARES OCUPADOS. Es la
     misma familia que R1: la cuenta se hace en SQL con el mismo predicado de
     cupos que usa el catalogo (incluido el timer de pending_no_receipt y el
     status de cada reserva), no con un "if" en la aplicacion. Una sola
     sentencia UPDATE con esa condicion, dentro de una transaccion que primero
     toma el lock de la fila del evento, para que una reserva simultanea no se
     cuele. Bajar la capacidad a un numero menor que lo vendido mostraria
     lugares negativos en el catalogo.

  3. LA IMAGEN DEL EVENTO QUEDA PENDIENTE. La columna image_url existe, pero

LA IDEA CENTRAL: RECHAZAR LIBERA EL CUPO SOLO

  No hay ningun contador de lugares. El predicado que cuenta lugares ocupados
  mira el ESTADO de la reserva: pending_review y approved ocupan; rejected,
  expired y cancelled no. Entonces:

    - APROBAR no mueve ningun numero: el lugar ya estaba retenido desde
      pending_review y sigue retenido en approved;
    - RECHAZAR libera el lugar por si solo, porque la fila deja de cumplir el
      predicado. No hay que restar nada a mano, y no existe la posibilidad de
      que un contador quede desincronizado con la realidad.

  Es el mismo criterio que ya regia en el catalogo (R1/R3): decide la base, no
  un "if" en la aplicacion que puede quedar viejo.

DECISIONES QUE CONVIENEN ENTENDER

  1. NO SE PUEDE APROBAR ALGO QUE NO PAGO. Solo se aprueba o rechaza lo que
     esta en pending_review. Una reserva sin comprobante (pending_no_receipt)
     no se aprueba: todavia no hay plata. La condicion va en el WHERE del
     UPDATE (status = 'pending_review'), asi que un doble clic o dos pestañas
     no aplican la transicion dos veces: la segunda no matchea ninguna fila y
     la pantalla lo dice, en vez de fingir exito.

  2. EL COMPROBANTE NO ES UN LINK PUBLICO. El bucket es privado, asi que el
     detalle pide una URL firmada y de vida corta en el momento de dibujar. Si
     Supabase no esta configurado (como en desarrollo local con Postgres), la
     pantalla NO se cae: muestra un aviso y sigue.

  3. LA CONDICION DE SALUD ES UN DATO SENSIBLE. El detalle la muestra (la
     dueña la necesita para organizar el encuentro), pero la LISTA no la trae
     a proposito: el listado es una cola de trabajo. Queda dentro del panel
     autenticado y no aparece en ninguna pagina publica. Ley 25.326.

  4. EL MOTIVO DEL RECHAZO ES OPCIONAL. Se guarda si lo escribis, y vacio se
     guarda como NULL (no como texto vacio), para poder distinguir "rechazada
     con una nota" de "rechazada sin decir nada". Avisarle a la persona que
     fue rechazada sigue siendo un pendiente (P3).

  5. LOS FILTROS VIENEN DE LA URL Y CUALQUIERA PUEDE EDITARLA. Un valor
     invalido (?status=loquesea) se IGNORA y muestra la lista completa; nunca
     un 500.

18. T10 - VENCIMIENTO Y SEGUIMIENTO (PAGINA PUBLICA POR TOKEN)
===============================================================================

QUE SE CONSTRUYO

  1. La regla de vencimiento quedo en UNA sola expresion SQL
     (effectiveStatusSql, en src/lib/reservations.ts), el espejo exacto del
     predicado de cupos:

       una reserva pending_no_receipt con expires_at vencido (o NULL)
       se presenta como "expirada"; todo lo demas, su estado guardado.

     La evalua el reloj de la base (el mismo que cuenta cupos), no
     JavaScript. Todo lo que muestra o filtra un estado usa ESA expresion:
     la lista del panel, el detalle, la pagina publica y las dos Server
     Actions que antes comparaban expiresAt en JavaScript (se eliminaron
     esas comparaciones: ya no hay ninguna copia de la regla en JS).

  2. La pagina publica /reservas/[token] dejo de mentir y distingue cada
     estado: retencion activa (con su fecha limite), en revision, confirmada,
     rechazada (con el motivo si la dueña lo escribio), VENCIDA ("el plazo
     vencio y el lugar se libero", con vuelta al evento) y cancelada. Antes,
     una retencion vencida seguia mostrando "Te guardamos el lugar" con una
     fecha pasada, y todo lo demas caia en un texto generico.

  3. La pagina publica hace UNA consulta (antes dos, una redundante) y nunca
     selecciona la condicion de salud: es un dato sensible y esta pagina se
     abre solo con un token, sin login.

  4. El panel: el badge muestra el estado efectivo, y el filtro "Expirada"
     ahora devuelve las que vencieron por timer (antes devolvia vacio porque
     miraba el estado guardado).

EL DEFECTO REAL QUE LA VERIFICACION ENCONTRO Y SE CORRIGIO

  Una retencion vencida nunca se persistia como expirada (el vencimiento es
  calculado al leer, R3). El indice unico parcial "una reserva activa por
  persona y evento" mira el estado GUARDADO, asi que la persona quedaba
  bloqueada para siempre: no podia volver a reservar el mismo evento, con el
  cupo libre. El comentario del propio indice decia que una reserva expirada
  no bloquea un nuevo intento — la realidad lo desmentia. Prueba observada:
  occupied 1 -> (fuerzo expires_at al pasado) -> occupied 0 -> segunda reserva:
  already_reserved. La unica salida era usar otro email.

  Correccion: dentro de la MISMA transaccion de createReservation, despues
  del upsert del cliente y antes del insert, se materializa el vencimiento:

    UPDATE reservations SET status = 'expired', updated_at = now()
    WHERE event_id = ... AND customer_id = ... AND status = 'pending_no_receipt'
      AND (expires_at IS NULL OR expires_at <= now())

  Por que es segura:
    - la transaccion ya tiene la fila del evento con FOR UPDATE, asi que todos
      los intentos sobre ese evento estan serializados: no hay carrera;
    - la condicion es el complemento exacto del predicado de cupos, asi que
      nunca toca una retencion viva;
    - es idempotente;
    - no mueve ningun conteo: la fila ya habia dejado de contar.
  No hay migracion: ni el indice ni su predicado cambiaron, y el valor
  'expired' ya existia en el enum. Ahora la vuelta al evento de la pagina
  publica promete algo que la base cumple.
